# Rule 1 - 規範產出檔長相的才抽成樣板

- 強度：必須
- 口述或原文在規範「產出檔有哪些段落、什麼順序、每段寫成什麼形式」，抽成樣板。
- 口述或原文在規範「這一步怎麼判斷、怎麼取捨」，屬於條列式規則，不抽成樣板，改走 `/skill-derive-rule`。

| 規範的是什麼 | 例子 | 處理 |
| --- | --- | --- |
| 產出檔的長相 | 類別圖要有標題、mermaid 圖、類別職責清單 | 抽成樣板 |
| 步驟的判斷 | 只有 is-a 關係才畫繼承 | 改走 `/skill-derive-rule` |

## Good Example

- 為 `plan-with-class-diagram` Phase 2 步驟 2 抽樣板，使用者口述兩件事：第一件規範產出檔的段落，抽成樣板；第二件規範畫關係時怎麼判斷，改走 `/skill-derive-rule`。

1. 類別圖檔案要有標題、mermaid 圖、類別職責清單三段 → 抽成樣板
2. 只有 is-a 關係才畫繼承 → 改走 `/skill-derive-rule`，追加到 `類別關係選用原則.md`

## Bad Example

- 同樣兩件事都抽進樣板，第二件只能寫成骨架裡的註解。骨架被複製進產出檔時，判斷用的註解也跟著進去；而該步已 READ 的 `類別關係選用原則.md` 卻沒有這條規則。

```mermaid
classDiagram
  %% 只有 is-a 關係才畫繼承
  class {{類別名稱 1}}
  class {{類別名稱 2}}
  %% 依此類推
```

# Rule 2 - SOP 原文與既有 RuleFile 裡的格式描述也列入結構

- 強度：必須
- 除了使用者口述，目標步驟原文、目標步驟之前已 READ 的 RuleFile 裡描述產出格式的內容，也要列入產出檔案的結構。
- 每個段落都標出處：口述、SOP 原文或 RuleFile 檔名，讓使用者分得出哪些是從哪裡來的。

## Good Example

- 除了口述的三段，原文的「畫成 mermaid classDiagram」與 `mermaid-classdiagram-語法.md` 的節點標記也列入，並標出處。

```markdown
2. WRITE 依語法規範與關係選用原則，將 Phase 1 得出的類別組成畫成 mermaid classDiagram，存入 `docs/design/<功能名稱>-class-diagram.md`。
```

產出檔案結構：

1. 標題：`# <功能名稱> 類別圖`（出處：口述）
2. mermaid code block，內容為 `classDiagram`（出處：SOP 原文 Phase 2 步驟 2）
3. 類別節點寫成 `class ClassName { +publicMethod() }`（出處：`mermaid-classdiagram-語法.md` 節點標記）
4. `## 類別職責` 清單（出處：口述）

## Bad Example

- 同一步只列口述的段落，原文與 RuleFile 的格式描述沒有列入，也沒標出處。樣板裡沒有 mermaid code block，產出檔寫不出圖。

產出檔案結構：

1. 標題
2. 類別職責清單
