# SOP

## Phase 1 — 釐清開發範圍與現有類別

1. READ 使用者要新增或修改的功能需求。
2. READ 相關現有程式碼，找出可重用的既有類別、模組、介面。
3. THINK 推導出本次開發需要的類別／模組／介面、各自職責、屬性、方法與彼此關係（繼承／組合／依賴）。
   - 若專案非以物件導向類別組織 → 以 module／interface／struct 等節點彈性比擬類別圖元素。
4. ASK 需求範圍或類別邊界不明確時，向使用者確認範圍與邊界，取得明確答案後才進入 Phase 2。

**產出**：本次開發要呈現的類別組成清單（含各類別的職責與關係）。

## Phase 2 — 產出類別圖提案並確認

1. READ `rules/mermaid-classdiagram-語法.md`，取得類別圖標記規範。
2. WRITE 將 Phase 1 得出的類別組成畫成 mermaid classDiagram，存入設計文件（預設 `docs/design/<功能名稱>-class-diagram.md`）。
3. REPORT 向使用者展示類別圖與各類別的職責、彼此關係。
4. ASK 使用者是否核准此類別圖、可否進入開發。
   - 若不核准 → 退回步驟 2，依回饋調整類別圖後重新提案。

**產出**：使用者核准的類別圖設計文件。

## Phase 3 — 按圖施工

1. THINK 依類別圖的依賴關係，排出開發順序（被依賴者優先於依賴者）。
2. WRITE 依排定順序逐一將每個類別／模組實作到對應的程式碼檔案。
3. CHECK 每完成一個類別，核對其是否符合類別圖定義的職責與介面。
   - 若不符 → 退回步驟 2 修正該類別，完成後再次 CHECK。

**產出**：依核准類別圖完成、且順序正確的程式碼實作。
