# SOP

## Phase 1 — 釐清範圍與現有類別

1. READ 使用者要新增或修改的功能需求。
2. READ 相關現有程式碼，找出可重用的既有類別、模組、介面。
3. READ `rules/類別設計原則.md`。
4. THINK 依類別設計原則，推導出本次開發需要的類別／模組／介面、各自職責、屬性、方法與彼此關係。
5. ASK 需求範圍或類別邊界不明確時，向使用者確認範圍與邊界，取得明確答案後才進入 Phase 2。

**產出**：本次開發要呈現的類別組成清單（含各類別的職責與關係）。

## Phase 2 — 產出類別圖提案並確認

1. READ `rules/mermaid-classdiagram-語法.md` 與 `rules/類別關係選用原則.md`。
2. WRITE 依語法規範與關係選用原則，將 Phase 1 得出的類別組成畫成 mermaid classDiagram，存入 `docs/design/<功能名稱>-class-diagram.md`。
3. REPORT 向使用者展示類別圖與各類別的職責、彼此關係。
4. ASK 使用者是否核准此類別圖，取得核准才進入 Phase 3。
   - 若不核准 → 退回步驟 2，依回饋調整類別圖後重新提案。

**產出**：使用者核准的類別圖設計文件。

## Phase 3 — 依類別圖實作程式

1. READ `rules/開發順序排序規則.md`。
2. THINK 依開發順序排序規則，依類別圖的依賴關係排出開發順序。
   - 若依賴鏈出現環 → 退回 Phase 2 步驟 2 修圖，重新取得核准後再繼續。
3. WRITE 依排定順序逐一將每個類別／模組實作到對應的程式碼檔案。
4. READ `rules/實作一致性核對規則.md`。
5. CHECK 每完成一個類別，依實作一致性核對規則核對其是否符合類別圖定義的職責與介面。
   - 若是實作有誤 → 退回步驟 3 修正該類別，完成後再次 CHECK。
   - 若是類別圖本身需要變更 → 退回 Phase 2 步驟 2 修圖，重新取得核准後再繼續。
6. REPORT 交出實作結果，列出各類別對應的程式碼檔案與開發順序。

**產出**：依核准類別圖完成、且順序正確的程式碼實作。
