# Rule 1 - 實作的 public 方法簽章需與類別圖一致

- 強度：必須
- 類別圖上定義的每個 `+method()`，實作裡都要有名稱、參數一致的 public 方法。
- 實作不可以有類別圖上沒畫出來的額外 public 方法（語言強制的樣板方法除外，例如建構子、`__str__`）。

## Good Example

- 類別圖只定義了 `placeOrder(items)` 一個 public 方法，實作也只公開這一個方法，其餘輔助邏輯都是 private。

```
class OrderService {
  +placeOrder(items)
  -validateStock(items)
}
```

```python
class OrderService:
    def place_order(self, items):
        self._validate_stock(items)
        ...

    def _validate_stock(self, items):
        ...
```

## Bad Example

- 實作多出了類別圖上沒畫的 public 方法 `cancel_order`，呼叫端可能因此依賴了一個沒有經過設計審視、圖上也查不到的介面。

```
class OrderService {
  +placeOrder(items)
  -validateStock(items)
}
```

```python
class OrderService:
    def place_order(self, items):
        self._validate_stock(items)
        ...

    def cancel_order(self, order_id):
        ...

    def _validate_stock(self, items):
        ...
```

# Rule 2 - 類別圖標記 private 的成員不可在實作中變成 public

- 強度：必須
- 類別圖上用 `-` 標記的欄位/方法，實作裡的存取層級要維持私有（或該語言對等的封裝層級），不能對外公開。

## Good Example

- `validateStock` 在圖上是 `-`（private），實作用底線前綴（Python 的私有慣例）維持私有，外部呼叫者拿不到。

```
class OrderService {
  +placeOrder(items)
  -validateStock(items)
}
```

```python
class OrderService:
    def place_order(self, items):
        self._validate_stock(items)

    def _validate_stock(self, items):
        ...
```

## Bad Example

- `validateStock` 在圖上是 private，實作卻拿掉底線變成沒有封裝的 public 方法，外部呼叫者可以繞過 `place_order` 直接呼叫驗證邏輯，破壞了圖上設計的封裝邊界。

```
class OrderService {
  +placeOrder(items)
  -validateStock(items)
}
```

```python
class OrderService:
    def place_order(self, items):
        self.validate_stock(items)

    def validate_stock(self, items):
        ...
```

# Rule 3 - 關係型別要對應到程式碼的實作方式

- 強度：必須
- 圖上畫 composition 的關係，實作裡部分物件的建立與銷毀必須由整體完全控制（例如只在整體內部建立，不對外提供可以單獨取得或替換它的介面）。
- 圖上畫 aggregation 的關係，實作裡整體只能透過建構子參數或方法參數拿到外部建立好的部分物件，不能自己在內部 new 出來據為己有。

## Good Example

- 圖上 `Order *-- OrderItem` 是 composition，實作裡 `OrderItem` 只能透過 `Order.add_item` 在內部建立，外部沒有辦法脫離 `Order` 單獨建立或取得它的參照長期持有。

```
class Order {
  +addItem(sku, quantity)
}
class OrderItem {
  +sku
  +quantity
}
Order *-- OrderItem
```

```python
class Order:
    def __init__(self):
        self._items = []

    def add_item(self, sku, quantity):
        self._items.append(OrderItem(sku, quantity))
```

## Bad Example

- 圖上畫的是 composition，但實作讓呼叫端自己 `OrderItem(...)` 建立後傳進來給 `Order` 持有，`OrderItem` 其實可以脫離 `Order` 獨立建立、被其他物件持有，實作的所有權關係其實是 aggregation，跟圖上畫的不一致。

```
class Order {
  +addItem(item)
}
class OrderItem {
  +sku
  +quantity
}
Order *-- OrderItem
```

```python
class Order:
    def __init__(self):
        self._items = []

    def add_item(self, item: OrderItem):
        self._items.append(item)

# 呼叫端：
item = OrderItem(sku="A1", quantity=2)
order.add_item(item)
```

# Rule 4 - 依賴關係要與圖雙向對應，不多不少

- 強度：必須
- 圖上每一條依賴/關聯/繼承/實作介面的箭頭，程式碼裡都要找得到對應的 import、欄位型別或繼承/實作宣告。
- 程式碼裡每一個對其他類別的 import 或型別使用，圖上都要畫得出對應的箭頭；找不到對應箭頭的依賴視為圖未涵蓋，需要退回補圖或視為實作誤植。

## Good Example

- 圖上畫了 `OrderService --> PaymentGateway`，實作裡 `OrderService` 確實 import 並持有 `PaymentGateway` 型別的欄位，兩邊一一對應，沒有圖上沒畫但程式碼裡多出來的依賴。

```
class OrderService {
  -paymentGateway
  +placeOrder(items)
}
class PaymentGateway {
  <<interface>>
  +charge(amount)
}
OrderService --> PaymentGateway
```

```python
from payment_gateway import PaymentGateway

class OrderService:
    def __init__(self, payment_gateway: PaymentGateway):
        self._payment_gateway = payment_gateway
```

## Bad Example

- 圖上只畫了 `OrderService --> PaymentGateway`，但實作裡多 import 並呼叫了一個圖上完全沒出現的 `InventoryService`，這條依賴沒有經過類別圖的設計審視就被加進來，兩邊對不上。

```
class OrderService {
  -paymentGateway
  +placeOrder(items)
}
class PaymentGateway {
  <<interface>>
  +charge(amount)
}
OrderService --> PaymentGateway
```

```python
from payment_gateway import PaymentGateway
from inventory_service import InventoryService

class OrderService:
    def __init__(self, payment_gateway: PaymentGateway):
        self._payment_gateway = payment_gateway
        self._inventory_service = InventoryService()
```
