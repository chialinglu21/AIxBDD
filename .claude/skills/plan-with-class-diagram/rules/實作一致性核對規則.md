# Rule 1 - 實作的 public 方法簽章需與類別圖一致

- 強度：必須
- 類別圖上定義的每個 `+method()`，實作裡都要有名稱、參數一致的 public 方法。
- 實作不可以有類別圖上沒畫出來的額外 public 方法（語言強制的樣板方法除外，例如 `constructor`）。

## Good Example

- 類別圖只定義了 `placeOrder(items)` 一個 public 方法，實作也只公開這一個方法，其餘輔助邏輯都是 private。

```
class OrderService {
  +placeOrder(Array~string~ items)
  -validateStock(Array~string~ items)
}
```

```ts
export class OrderService {
  placeOrder(items: Array<string>): void {
    this.validateStock(items);
  }

  private validateStock(items: Array<string>): void {
    if (items.length === 0) throw new Error('items is empty');
  }
}
```

## Bad Example

- 實作多出了類別圖上沒畫的 public 方法 `cancelOrder`，呼叫端可能因此依賴了一個沒有經過設計審視、圖上也查不到的介面。

```
class OrderService {
  +placeOrder(Array~string~ items)
  -validateStock(Array~string~ items)
}
```

```ts
export class OrderService {
  placeOrder(items: Array<string>): void {
    this.validateStock(items);
  }

  cancelOrder(orderId: string): void {
    console.log(`cancel ${orderId}`);
  }

  private validateStock(items: Array<string>): void {
    if (items.length === 0) throw new Error('items is empty');
  }
}
```

# Rule 2 - 類別圖標記 private 的成員不可在實作中變成 public

- 強度：必須
- 類別圖上用 `-` 標記的欄位/方法，實作裡的存取層級要維持私有（用 `private` 修飾詞或 `#` 私有欄位），不能對外公開。
- TypeScript 成員沒寫修飾詞時預設是 public，所以私有成員一定要明確標示。

## Good Example

- `validateStock` 在圖上是 `-`（private），實作用 `private` 修飾詞維持私有，外部呼叫者在編譯時就拿不到。

```
class OrderService {
  +placeOrder(Array~string~ items)
  -validateStock(Array~string~ items)
}
```

```ts
export class OrderService {
  placeOrder(items: Array<string>): void {
    this.validateStock(items);
  }

  private validateStock(items: Array<string>): void {
    if (items.length === 0) throw new Error('items is empty');
  }
}
```

## Bad Example

- `validateStock` 在圖上是 private，實作卻拿掉 `private` 變成預設的 public 方法，外部呼叫者可以繞過 `placeOrder` 直接呼叫驗證邏輯，破壞了圖上設計的封裝邊界。

```
class OrderService {
  +placeOrder(Array~string~ items)
  -validateStock(Array~string~ items)
}
```

```ts
export class OrderService {
  placeOrder(items: Array<string>): void {
    this.validateStock(items);
  }

  validateStock(items: Array<string>): void {
    if (items.length === 0) throw new Error('items is empty');
  }
}
```

# Rule 3 - 關係型別要對應到程式碼的實作方式

- 強度：必須
- 圖上畫 composition 的關係，實作裡部分物件的建立與銷毀必須由整體完全控制（例如只在整體內部建立，不對外提供可以單獨取得或替換它的介面）。
- 圖上畫 aggregation 的關係，實作裡整體只能透過建構子參數或方法參數拿到外部建立好的部分物件，不能自己在內部 `new` 出來據為己有。

## Good Example

- 圖上 `Order *-- OrderItem` 是 composition，實作裡 `OrderItem` 只能透過 `Order.addItem` 在內部建立，外部沒有辦法脫離 `Order` 單獨建立或取得它的參照長期持有。

```
class Order {
  +addItem(string sku, number quantity)
}
class OrderItem {
  +string sku
  +number quantity
}
Order *-- OrderItem
```

```ts
export class Order {
  private items: OrderItem[] = [];

  addItem(sku: string, quantity: number): void {
    this.items.push(new OrderItem(sku, quantity));
  }
}
```

## Bad Example

- 圖上畫的是 composition，但實作讓呼叫端自己 `new OrderItem(...)` 建立後傳進來給 `Order` 持有，`OrderItem` 其實可以脫離 `Order` 獨立建立、被其他物件持有，實作的所有權關係其實是 aggregation，跟圖上畫的不一致。

```
class Order {
  +addItem(OrderItem item)
}
class OrderItem {
  +string sku
  +number quantity
}
Order *-- OrderItem
```

```ts
export class Order {
  private items: OrderItem[] = [];

  addItem(item: OrderItem): void {
    this.items.push(item);
  }
}

// 呼叫端：
const item = new OrderItem('A1', 2);
order.addItem(item);
```

# Rule 4 - 依賴關係要與圖雙向對應，不多不少

- 強度：必須
- 圖上每一條依賴/關聯/繼承/實作介面的箭頭，程式碼裡都要找得到對應的 `import`、欄位型別或 `extends`／`implements` 宣告。
- 程式碼裡每一個對其他類別的 `import` 或型別使用，圖上都要畫得出對應的箭頭；找不到對應箭頭的依賴視為圖未涵蓋，需要退回補圖或視為實作誤植。

## Good Example

- 圖上畫了 `OrderService --> PaymentGateway`，實作裡 `OrderService` 確實 `import` 並持有 `PaymentGateway` 型別的欄位，兩邊一一對應，沒有圖上沒畫但程式碼裡多出來的依賴。

```
class OrderService {
  -PaymentGateway paymentGateway
  +placeOrder(Array~string~ items)
}
class PaymentGateway {
  <<interface>>
  +charge(number amount) boolean
}
OrderService --> PaymentGateway
```

```ts
import { PaymentGateway } from './PaymentGateway';

export class OrderService {
  constructor(private readonly paymentGateway: PaymentGateway) {}
}
```

## Bad Example

- 圖上只畫了 `OrderService --> PaymentGateway`，但實作裡多 `import` 並使用了一個圖上完全沒出現的 `InventoryService`，這條依賴沒有經過類別圖的設計審視就被加進來，兩邊對不上。

```
class OrderService {
  -PaymentGateway paymentGateway
  +placeOrder(Array~string~ items)
}
class PaymentGateway {
  <<interface>>
  +charge(number amount) boolean
}
OrderService --> PaymentGateway
```

```ts
import { PaymentGateway } from './PaymentGateway';
import { InventoryService } from './InventoryService';

export class OrderService {
  private readonly inventoryService = new InventoryService();

  constructor(private readonly paymentGateway: PaymentGateway) {}
}
```

# Rule 5 - 實作的欄位、參數與回傳型別需與類別圖一致

- 強度：必須
- 類別圖上每個屬性標的型別，實作裡對應欄位的型別要相同。
- 類別圖上每個方法參數標的型別，實作裡對應參數的型別要相同。
- 類別圖上方法括號後標的回傳型別，實作裡的回傳型別要相同；括號後沒標回傳型別的方法，實作要回傳 `void`。

## Good Example

- `status` 是 `string`、`canTransition` 參數是 `string`、回傳 `boolean`，實作的型別逐一對得上圖。

```
class Order {
  +string id
  +string status
  +canTransition(string event) boolean
}
```

```ts
export class Order {
  constructor(public id: string, public status: string) {}

  canTransition(event: string): boolean {
    return this.status !== 'shipped' && event !== '';
  }
}
```

## Bad Example

- 圖上 `canTransition` 回傳 `boolean`，實作卻改成回傳 `string` 錯誤訊息，呼叫端照圖寫 `if (order.canTransition(event))` 時，不能轉換（回傳錯誤訊息）反而被當成 true，判斷結果剛好相反。

```
class Order {
  +string id
  +string status
  +canTransition(string event) boolean
}
```

```ts
export class Order {
  constructor(public id: string, public status: string) {}

  canTransition(event: string): string {
    return this.status === 'shipped' ? 'order already shipped' : '';
  }
}
```
