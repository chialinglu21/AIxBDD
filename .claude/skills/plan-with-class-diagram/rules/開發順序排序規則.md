# Rule 1 - 六種關係符號都算依賴，由箭頭左端依賴右端

- 強度：必須
- `--|>`、`*--`、`o--`、`-->`、`..>`、`..|>` 六種關係符號都算依賴，不只 `..>`。
- 每條關係一律由箭頭左端的類別依賴右端的類別，右端要先開發。

| 關係 | 範例 | 先開發 |
| --- | --- | --- |
| 繼承 `--\|>` | `Child --\|> Parent` | `Parent` |
| 組合 `*--` | `Order *-- OrderItem` | `OrderItem` |
| 聚合 `o--` | `Team o-- Player` | `Player` |
| 關聯 `-->` | `OrderService --> PaymentGateway` | `PaymentGateway` |
| 依賴 `..>` | `OrderService ..> EmailFormatter` | `EmailFormatter` |
| 實作介面 `..\|>` | `StripeGateway ..\|> PaymentGateway` | `PaymentGateway` |

## Good Example

- 組合 `*--` 也算依賴，整體 `Order` 依賴部分 `OrderItem`，所以 `OrderItem` 先開發。

```
class Order {
  +orderId
  +addItem(item)
}
class OrderItem {
  +sku
  +quantity
}
Order *-- OrderItem
```

開發順序：

1. `OrderItem`
2. `Order`

## Bad Example

- 只把 `-->`、`..>` 當依賴，漏看 `*--`，`Order` 排在 `OrderItem` 前面，實作 `Order` 時 import 不到 `OrderItem`。

```
class Order {
  +orderId
  +addItem(item)
}
class OrderItem {
  +sku
  +quantity
}
Order *-- OrderItem
```

開發順序：

1. `Order`
2. `OrderItem`

# Rule 2 - 依整條依賴鏈分層，由低層排到高層

- 強度：必須
- 沒有任何依賴的類別是第 0 層，包含圖上沒有任何關係線的孤立類別。
- 其餘類別的層數是它所依賴的類別中最大的層數加 1。
- 開發順序由低層排到高層，不只比對相鄰兩個類別。

## Good Example

- `OrderService` 依賴 `Order`、`Order` 依賴 `OrderItem`，層數沿著依賴鏈逐層加 1：`OrderItem` 第 0 層、`Order` 第 1 層、`OrderService` 第 2 層。

```
class OrderService {
  +placeOrder(items)
}
class Order {
  +addItem(item)
}
class OrderItem {
  +sku
}
OrderService --> Order
Order *-- OrderItem
```

開發順序：

1. `OrderItem`（第 0 層）
2. `Order`（第 1 層）
3. `OrderService`（第 2 層）

## Bad Example

- 用「直接依賴的個數」當層數，`Order` 和 `OrderService` 都只有 1 個直接依賴而被排進同一層，同層依宣告順序，`OrderService` 排在 `Order` 前面。

```
class OrderService {
  +placeOrder(items)
}
class Order {
  +addItem(item)
}
class OrderItem {
  +sku
}
OrderService --> Order
Order *-- OrderItem
```

開發順序：

1. `OrderItem`
2. `OrderService`
3. `Order`

# Rule 3 - 依賴鏈出現環時不排序，列出環上的類別

- 強度：必須
- 依賴鏈出現環時，環上的類別無法分層，不產出開發順序。
- 列出環上的所有類別，並視為類別圖缺陷。
- 不自行挑一條邊切斷或忽略，也不自行改圖。

## Good Example

- `OrderService` 與 `InventoryService` 互相依賴，無法分層，所以列出環上的類別，不產出順序。

```
class OrderService {
  +placeOrder(items)
}
class InventoryService {
  +reserveStock(sku, qty)
}
OrderService --> InventoryService
InventoryService --> OrderService
```

結果：

- 環：`OrderService` → `InventoryService` → `OrderService`
- 類別圖有缺陷，不產出開發順序。

## Bad Example

- 自行忽略 `InventoryService --> OrderService` 這條邊，硬排出順序，等於偷偷改了已核准的類別圖，也讓實作裡那條依賴對不到圖。

```
class OrderService {
  +placeOrder(items)
}
class InventoryService {
  +reserveStock(sku, qty)
}
OrderService --> InventoryService
InventoryService --> OrderService
```

開發順序：

1. `InventoryService`
2. `OrderService`

# Rule 4 - 同層類別依類別圖的宣告順序排

- 強度：建議
- 同一層的類別彼此沒有依賴，依它們在類別圖檔案中宣告 `class` 的先後排。
- 不依字母、重要性或個人判斷調整同層順序。

## Good Example

- `OrderService` 與 `StripeGateway` 都在第 1 層，`OrderService` 先宣告，所以排在前面。

```
class OrderService {
  -paymentGateway
  +placeOrder(items)
}
class PaymentGateway {
  <<interface>>
  +charge(amount)
}
class StripeGateway {
  +charge(amount)
}
OrderService --> PaymentGateway
StripeGateway ..|> PaymentGateway
```

開發順序：

1. `PaymentGateway`（第 0 層）
2. `OrderService`（第 1 層）
3. `StripeGateway`（第 1 層）

## Bad Example

- 憑「具體實作比較重要」把 `StripeGateway` 排到 `OrderService` 前面，不同人做出的順序不一樣，回報的開發順序無法重現。

```
class OrderService {
  -paymentGateway
  +placeOrder(items)
}
class PaymentGateway {
  <<interface>>
  +charge(amount)
}
class StripeGateway {
  +charge(amount)
}
OrderService --> PaymentGateway
StripeGateway ..|> PaymentGateway
```

開發順序：

1. `PaymentGateway`（第 0 層）
2. `StripeGateway`（第 1 層）
3. `OrderService`（第 1 層）
