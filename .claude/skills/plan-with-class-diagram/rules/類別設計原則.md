# Rule 1 - 一個類別只負責一件事（單一職責），避免職責堆疊成 God Class

- 強度：必須
- 類別的職責邊界對應到需求裡的一個名詞或一個「異動原因」，不合併兩個不相關的異動原因到同一個類別。
- 若職責說明需要用「和」字連接兩件不相關的事，就該拆分成兩個類別。
- 類別的屬性/方法數量明顯多於同一張圖裡其他類別（例如超過其他類別平均的 2 倍以上），或同時管理三個以上不同名詞的狀態，視為職責堆疊過多的訊號，需要拆分。

## Good Example

- 「訂單狀態轉換」「開立發票」「庫存」「會員點數」四個不同異動原因分別由 `OrderService`、`InvoiceIssuer`、`InventoryService`、`LoyaltyPointService` 負責，各自的方法數量都差不多、職責範圍都能一句話講完。

```
class OrderService {
  +placeOrder(Array~string~ items)
  +cancelOrder(string orderId)
  +markAsShipped(string orderId)
}
class InvoiceIssuer {
  +issueInvoice(Order order)
  -calculateTax(number amount) number
}
class InventoryService {
  +reserveStock(string sku, number qty)
  +releaseStock(string sku, number qty)
}
class LoyaltyPointService {
  +addPoints(string memberId, number amount)
  +redeemPoints(string memberId, number amount)
}
```

## Bad Example

- `OrderService` 把「訂單狀態轉換」「開立發票」「庫存」「會員點數」四個不相關的異動原因全部塞進同一個類別，職責說明需要用「和」字串起四件事，方法數量也遠多於其他類別。

```
class OrderService {
  +placeOrder(Array~string~ items)
  +cancelOrder(string orderId)
  +markAsShipped(string orderId)
  +issueInvoice(Order order)
  -calculateTax(number amount) number
  +reserveStock(string sku, number qty)
  +releaseStock(string sku, number qty)
  +addPoints(string memberId, number amount)
  +redeemPoints(string memberId, number amount)
}
```

# Rule 2 - 高階類別依賴抽象，不依賴具體實作

- 強度：必須
- 需要呼叫外部服務或未來可能替換實作的類別，依賴 interface/type，不直接依賴另一個具體類別。
- 類別圖上，高階類別對外部服務的關係箭頭指向 `<<interface>>` 節點，再由具體實作 `..|>` 該介面。

## Good Example

- `OrderService` 依賴 `<<interface>> PaymentGateway`，實際用哪家金流（`StripeGateway`）都實作這個介面，換金流不用改 `OrderService`。

```
class OrderService {
  -PaymentGateway paymentGateway
  +placeOrder(Array~string~ items)
}
class PaymentGateway {
  <<interface>>
  +charge(number amount) boolean
}
class StripeGateway {
  +charge(number amount) boolean
}
OrderService --> PaymentGateway
StripeGateway ..|> PaymentGateway
```

## Bad Example

- `OrderService` 直接依賴具體的 `StripeGateway`，要換成別家金流就要改 `OrderService` 的程式碼。

```
class OrderService {
  -StripeGateway stripeGateway
  +placeOrder(Array~string~ items)
}
class StripeGateway {
  +charge(number amount) boolean
}
OrderService --> StripeGateway
```

# Rule 3 - 依不同呼叫者拆分介面

- 強度：建議
- 一個類別被兩種不相關的呼叫者使用、且各自只需要不同子集的方法時，拆出對應各自需求的 interface，不共用一個大介面。
- 呼叫者不應該被迫依賴自己用不到的方法。

## Good Example

- 後台報表只需要查詢訂單，不需要建立/取消訂單，所以拆出 `OrderReader` 給報表用；下單流程才用完整的 `OrderWriter`，兩者互不干擾。

```
class OrderReader {
  <<interface>>
  +getOrder(string orderId) Order
  +listOrders(OrderFilter filter) Array~Order~
}
class OrderWriter {
  <<interface>>
  +placeOrder(Array~string~ items)
  +cancelOrder(string orderId)
}
class OrderService {
  +getOrder(string orderId) Order
  +listOrders(OrderFilter filter) Array~Order~
  +placeOrder(Array~string~ items)
  +cancelOrder(string orderId)
}
OrderService ..|> OrderReader
OrderService ..|> OrderWriter
```

## Bad Example

- 報表模組被迫依賴整個 `OrderRepository` 介面，即使它只用得到查詢方法；下單流程改了 `placeOrder` 簽章，報表模組的依賴也會被迫重新確認。

```
class OrderRepository {
  <<interface>>
  +getOrder(string orderId) Order
  +listOrders(OrderFilter filter) Array~Order~
  +placeOrder(Array~string~ items)
  +cancelOrder(string orderId)
}
class OrderService {
  +getOrder(string orderId) Order
  +listOrders(OrderFilter filter) Array~Order~
  +placeOrder(Array~string~ items)
  +cancelOrder(string orderId)
}
OrderService ..|> OrderRepository
```

# Rule 4 - 命名要直接體現職責，不用掩蓋職責的空詞

- 強度：建議
- 類別名稱要讓人一看就知道它負責什麼，不用 Manager、Helper、Util、Common 這類沒有具體職責意涵的空詞。
- 找不到更精準名稱時，先問「這個類別真正在做的那件事叫什麼」，用那個動作或名詞命名。

## Good Example

- `InvoiceIssuer` 直接說出職責是「開立發票」，看名稱就知道要找哪個類別改稅務邏輯。

```
class InvoiceIssuer {
  +issueInvoice(Order order)
}
```

## Bad Example

- `OrderManager` 沒有說出具體職責，日後容易變成什麼都塞進去的類別（違反 Rule 1 的單一職責）。

```
class OrderManager {
  +issueInvoice(Order order)
}
```

# Rule 5 - 屬性寫成「型別 名稱」標出型別

- 強度：必須
- 每個屬性都寫出型別，型別放在名稱前面，中間空一格。
- 型別用目標專案語言的型別名稱。
- 泛型的型別參數用 `~` 包住，不用 `<>`。

```
+string status
-Array~OrderItem~ items
```

## Good Example

- `Order` 的 `id`、`status` 都標出型別，實作時不用猜 `status` 是字串還是列舉。

```
class Order {
  +string id
  +string status
  +canTransition(string event) boolean
}
```

## Bad Example

- `id`、`status` 只有名稱沒有型別，實作者要自己猜型別，Phase 3 也無從核對實作的欄位型別是否正確。

```
class Order {
  +id
  +status
  +canTransition(string event) boolean
}
```

# Rule 6 - 方法參數寫成「型別 名稱」標出型別

- 強度：必須
- 方法的每個參數都寫出型別，型別放在參數名稱前面，中間空一格。
- 多個參數用 `, ` 分隔。
- 型別寫法同 Rule 5。

```
+transition(string orderId, string event)
```

## Good Example

- `validate` 的第一個參數標成 `Order order`，一看就知道傳入的是整個訂單物件，不是訂單編號。

```
class OrderService {
  +transition(string orderId, string event)
  -validate(Order order, string event)
}
class Order {
  +string id
  +string status
  +canTransition(string event) boolean
}
OrderService --> Order
```

## Bad Example

- 參數只寫名稱，看不出 `validate(order, event)` 的 `order` 是 `Order` 物件還是訂單編號字串，呼叫端與實作端可能各自理解成不同型別。

```
class OrderService {
  +transition(orderId, event)
  -validate(order, event)
}
class Order {
  +string id
  +string status
  +canTransition(string event) boolean
}
OrderService --> Order
```

# Rule 7 - 方法有回傳值時在括號後標出回傳型別，沒有回傳值就不寫

- 強度：必須
- 有回傳值的方法，在參數括號之後空一格寫回傳型別。
- 沒有回傳值（void）的方法，括號後面什麼都不寫，不寫 `void`。
- 回傳型別寫法同 Rule 5。

```
+findById(string id) Order
+save(Order order)
```

## Good Example

- `canTransition` 回傳 `boolean`、`findById` 回傳 `Order`，都標在括號後；`save` 沒有回傳值，括號後留空。

```
class OrderRepository {
  <<interface>>
  +findById(string id) Order
  +save(Order order)
}
class Order {
  +string id
  +string status
  +canTransition(string event) boolean
}
OrderRepository ..> Order
```

## Bad Example

- `canTransition`、`findById` 沒標回傳型別，看不出一個回傳布林、一個回傳訂單物件；`save` 沒有回傳值卻寫了 `void`，和「不寫就是沒有回傳值」的約定不一致。

```
class OrderRepository {
  <<interface>>
  +findById(string id)
  +save(Order order) void
}
class Order {
  +string id
  +string status
  +canTransition(string event)
}
OrderRepository ..> Order
```

# Rule 8 - 型別用到圖上其他類別時畫出關係線

- 強度：必須
- 屬性、參數或回傳型別（含泛型的型別參數）用到圖上另一個類別時，兩個類別之間必須有關係線，由使用方指向被使用方。
- 本條只要求不可漏畫，關係線的種類依 `類別關係選用原則.md` 決定。
- 語言內建型別（例如 `string`、`number`、`boolean`、`Array`）不用畫關係線。

## Good Example

- `findById` 回傳 `Order`、`save` 參數是 `Order`，所以畫出 `OrderRepository ..> Order`，Phase 3 排序時 `Order` 會排在 `OrderRepository` 之前。

```
class OrderRepository {
  <<interface>>
  +findById(string id) Order
  +save(Order order)
}
class Order {
  +string id
  +string status
  +canTransition(string event) boolean
}
OrderRepository ..> Order
```

## Bad Example

- 型別用到 `Order` 卻沒畫關係線，兩個類別都被當成第 0 層、依宣告順序先做 `OrderRepository`，實作時 import 不到 `Order`；程式碼裡的 `import Order` 也找不到對應箭頭。

```
class OrderRepository {
  <<interface>>
  +findById(string id) Order
  +save(Order order)
}
class Order {
  +string id
  +string status
  +canTransition(string event) boolean
}
```
