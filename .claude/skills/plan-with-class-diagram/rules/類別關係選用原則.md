# Rule 1 - 整體與部分生命週期綁定時用 composition

- 強度：必須
- 部分只依附在該整體底下存在，整體被刪除/消滅時部分也要一併消失，且沒有部分被其他整體共用的情況，畫 composition（`*--`）。
- 部分的建立與銷毀完全由整體控制，不對外公開讓其他物件單獨建立它。

## Good Example

- `OrderItem` 只在某張 `Order` 底下才有意義，訂單被刪除時底下的明細也一起刪除，沒有明細被兩張訂單共用的情況。

```
class Order {
  +string orderId
  +addItem(string sku, number quantity)
}
class OrderItem {
  +string sku
  +number quantity
}
Order *-- OrderItem
```

## Bad Example

- 把「訂單刪除、明細也跟著刪除」這種生命週期綁定的關係畫成 aggregation，暗示 `OrderItem` 可以脫離 `Order` 獨立存在或被其他訂單共用，跟實際規則不符。

```
class Order {
  +string orderId
  +addItem(string sku, number quantity)
}
class OrderItem {
  +string sku
  +number quantity
}
Order o-- OrderItem
```

# Rule 2 - 部分可獨立存在或被共用時用 aggregation

- 強度：必須
- 部分的生命週期不受整體控制，整體消失時部分仍可繼續存在，或同一個部分可以同時屬於多個整體，畫 aggregation（`o--`）。

## Good Example

- `Player` 不會因為 `Team` 解散就消失，同一個 `Player` 也可能轉隊到另一個 `Team`，兩者生命週期各自獨立。

```
class Team {
  +string teamName
  +addPlayer(Player player)
}
class Player {
  +string playerName
}
Team o-- Player
```

## Bad Example

- 畫成 composition，暗示 `Team` 解散時 `Player` 也要跟著消滅、且不能轉隊到別隊，跟球員實際可以獨立存在、轉隊的事實不符。

```
class Team {
  +string teamName
  +addPlayer(Player player)
}
class Player {
  +string playerName
}
Team *-- Player
```

# Rule 3 - 只是持有參照、沒有所有權關係時用 association

- 強度：必須
- 一個類別長期持有另一個類別的參照（通常是欄位），但兩者沒有生命週期綁定、也沒有整體/部分關係，畫一般 association（`-->`）。

## Good Example

- `OrderService` 長期持有一個 `PaymentGateway` 的參照來呼叫扣款，但 `PaymentGateway` 不是 `OrderService` 的一部分，也不會隨 `OrderService` 的生死而生死。

```
class OrderService {
  -PaymentGateway paymentGateway
  +placeOrder(Array~string~ items)
}
class PaymentGateway {
  <<interface>>
  +charge(number amount) boolean
}
OrderService --> PaymentGateway
```

## Bad Example

- 把單純的欄位參照畫成 composition，暗示 `PaymentGateway` 是 `OrderService` 的一部分、會隨 `OrderService` 消滅，但金流服務其實是被多個服務共用的獨立元件。

```
class OrderService {
  -PaymentGateway paymentGateway
  +placeOrder(Array~string~ items)
}
class PaymentGateway {
  <<interface>>
  +charge(number amount) boolean
}
OrderService *-- PaymentGateway
```

# Rule 4 - 只在方法內短暫使用、不是欄位持有時用 dependency

- 強度：必須
- 類別只在某個方法的參數或區域變數用到另一個類別、沒有把它存成欄位長期持有，畫 dependency（`..>`），不要畫成 association。

## Good Example

- `OrderService.placeOrder` 方法內用區域變數建立一個 `EmailFormatter` 來組信件內容，用完即丟，`OrderService` 沒有把它存成欄位。

```
class OrderService {
  +placeOrder(Array~string~ items)
}
class EmailFormatter {
  +format(Order order) string
}
OrderService ..> EmailFormatter
```

## Bad Example

- 畫成長期持有的 association，暗示 `OrderService` 有一個欄位長期持有 `EmailFormatter`，但實際上它只在方法內臨時建立、用完就丟，關係強度被誇大了。

```
class OrderService {
  +placeOrder(Array~string~ items)
}
class EmailFormatter {
  +format(Order order) string
}
OrderService --> EmailFormatter
```

# Rule 5 - 不用繼承表達行為復用，繼承只用於「是一種」關係

- 強度：必須
- 只是想共用某段程式碼邏輯，不是子類別在語意上「是一種」父類別時，不能用繼承（`--|>`），改用 composition + 委派，把共用邏輯抽成獨立類別給雙方持有。
- 繼承只在「子類別的每個實例都能被當成父類別使用」（可替換性）成立時才使用。

## Good Example

- `SpecialOrder` 想重用折扣計算邏輯，但它在語意上並不是「一種」`DiscountCalculator`，所以把折扣邏輯抽成獨立的 `DiscountCalculator`，讓 `Order` 和 `SpecialOrder` 都透過 composition 持有它來複用。

```
class DiscountCalculator {
  +calculate(number subtotal) number
}
class Order {
  -DiscountCalculator discountCalculator
  +getTotal() number
}
class SpecialOrder {
  -DiscountCalculator discountCalculator
  +getTotal() number
}
Order *-- DiscountCalculator
SpecialOrder *-- DiscountCalculator
```

## Bad Example

- 讓 `SpecialOrder` 繼承 `Order` 只是為了重用折扣計算方法，但 `SpecialOrder` 其實不滿足「可以在任何用到 `Order` 的地方被替換」的條件（例如它的 `getTotal()` 回傳邏輯完全不同），繼承在這裡只是借用程式碼的手段。

```
class Order {
  +getTotal() number
  -calculateDiscount() number
}
class SpecialOrder {
  +getTotal() number
}
SpecialOrder --|> Order
```
