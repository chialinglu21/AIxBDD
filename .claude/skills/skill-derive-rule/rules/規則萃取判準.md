# Rule 1 - 目標步驟原文裡的判準也列為候選規則

- 強度：必須
- 除了使用者口述，目標步驟原文與其子句裡的判準也要列為候選規則，出處標「SOP 原文」。
- 決定產出內容的子句是判準，要萃取；決定流程走向的子句留在 SOP，不萃取。

| 子句在決定什麼 | 例子 | 處理 |
| --- | --- | --- |
| 產出內容怎麼定 | 主題相同就追加、新檔放在哪個路徑 | 萃取成規則 |
| 流程往哪走 | 不合就退回步驟 1、取得答案才往下 | 留在 SOP |

## Good Example

- 展開下面這一步時，兩個「若…」子句在決定 RuleFile 路徑，所以列為候選規則；同一份 SOP 裡「不合就退回步驟 1」決定的是流程，所以留著。

```markdown
5. THINK 依 RuleFile 歸屬判斷，比對使用者口述的規則主題與目標步驟已 READ 的 RuleFile 主題，定出 RuleFile 路徑。不必詢問使用者。
   - 若主題相同 → 追加到該 RuleFile。
   - 若主題不同或沒有既有 RuleFile → 新開 `<目標 skill>/rules/<主題>.md`。
```

候選規則：

1. 主題相同就追加到該 RuleFile（出處：SOP 原文 Phase 1 步驟 5）
2. 沒有同主題的 RuleFile 就新開 `<目標 skill>/rules/<檔名>.md`（出處：SOP 原文 Phase 1 步驟 5）

## Bad Example

- 同一步只萃取使用者口述的規則，兩個「若…」子句沒有列為候選。RuleFile 寫好之後，判準仍然只存在 SOP 上。

候選規則：

1. 比對範圍是同一 Phase 中目標步驟之前已 READ 的 RuleFile（出處：口述）
2. 規範的對象相同才算同一個主題（出處：口述）

# Rule 2 - 沒有口述時從相關檔案歸納草案並標出處

- 強度：必須
- 使用者沒有口述規則時，從目標步驟與目標 skill、相關 skill 的檔案歸納候選規則。
- 每條都標「歸納」與具體出處（哪個 skill、哪個 Phase 或哪個檔案），讓使用者分得出哪些是推出來的。

## Good Example

- 展開 Phase 1 步驟 5 時使用者沒有口述，每條候選規則都寫出是從哪裡歸納來的。

1. 規範的對象相同才算同一個主題（出處：歸納，`plan-with-class-diagram` Phase 2 步驟 1 同一行 READ 兩份不同主題的 RuleFile）
2. 新檔名與既有 RuleFile 重名時改為追加（出處：歸納，`skill-derive-rule` Phase 1「主題相同就追加」）

## Bad Example

- 同樣兩條規則沒有標出處，使用者會以為是自己說過的，或看不出是從哪裡推論出來的。

1. 規範的對象相同才算同一個主題
2. 新檔名與既有 RuleFile 重名時改為追加

# Rule 3 - 從步驟會分歧的判斷點找出需要的規則

- 強度：建議
- 逐一檢查目標步驟：兩個沒有上下文的人照做，會在哪個判斷點做出不同的東西。
- 每個會分歧的判斷點，至少要有一條候選規則把它寫死；不會分歧的地方不萃取規則。

## Good Example

- 「比對主題」是會分歧的判斷點：有人認為同一行 READ 就是同主題，有人認為要規範同一個對象才算。所以萃取出一條規則把它寫死。

```markdown
5. THINK 依 RuleFile 歸屬判斷，比對使用者口述的規則主題與目標步驟已 READ 的 RuleFile 主題，定出 RuleFile 路徑。不必詢問使用者。
```

候選規則：

1. 規範的對象相同才算同一個主題

## Bad Example

- 同一步萃取出的規則所管的事情，誰來做都會做得一樣；真正會分歧的「比對主題」反而沒有寫死。

候選規則：

1. THINK 時要仔細比對
2. 路徑要寫在 `rules/` 底下

# Rule 4 - 答得出「不照做會錯在哪」才萃取

- 強度：必須
- 每條候選規則都要說出：目標步驟不照它做時，會產出什麼具體的錯誤結果。
- 說不出具體錯誤結果的候選規則，不萃取。

## Good Example

- 「新檔名以規範的對象命名，不用步驟編號」答得出錯在哪：插入 READ 後編號推移，`phase3-step3.md` 指向的步驟 3 已經是 READ 本身。

1. 新檔名以規範的對象命名（不照做：插入 READ 後檔名指向錯誤的步驟）

## Bad Example

- 同一個命名主題，「檔名要取得好懂」說不出不照做會產出什麼錯誤，只是一句期許，卻被萃取成規則。

1. 新檔名要取得好懂

# Rule 5 - 已被既有規則涵蓋的不重複萃取

- 強度：必須
- 候選規則與比對範圍內 RuleFile 的某條規則要求相同時，丟掉這條候選規則。
- 丟掉時記下是被哪一份 RuleFile 的哪一條涵蓋，在 REPORT 時告訴使用者。

## Good Example

- 為 Phase 3 步驟 2 展開「READ 要放在被把關步驟前面」，`SOP-掛載規則.md` 的 Rule 2 已經規範了，所以丟掉，並記下涵蓋的位置。

候選規則：（無）

丟掉：READ 要放在被把關步驟前面（已被 `SOP-掛載規則.md` Rule 2 涵蓋）

## Bad Example

- 同一條候選規則沒有比對既有規則，直接追加成 Rule 7，同一件事在 `SOP-掛載規則.md` 裡寫了兩次。

```markdown
# Rule 2 - 新的 READ 緊貼在被把關步驟之前

- 強度：必須
- 新 RuleFile 的 READ 步驟插在被把關步驟的正前方，中間不夾其他步驟。

# Rule 7 - READ 要放在被把關步驟前面

- 強度：必須
- READ 步驟要放在它把關的那一步前面。
```

# Rule 6 - 與既有規則衝突時附上衝突分析

- 強度：必須
- 候選規則與既有規則衝突時，分析要列出：兩條規則的原文、各自在什麼情境下會產出什麼結果、採用任一方會影響哪些既有範例或步驟。
- 分析只陳述差異與影響，不替使用者決定採用哪一方。

## Good Example

- 使用者口述「READ 一律放在 Phase 開頭」，和 `SOP-掛載規則.md` Rule 2 衝突。分析寫出兩邊的原文、結果與影響範圍。

1. 口述：READ 一律放在 Phase 開頭。結果：Phase 3 的核對規則在排序、實作時就已載入。
2. 既有：`SOP-掛載規則.md` Rule 2「新的 READ 緊貼在被把關步驟之前」。結果：只在 CHECK 前才載入。
3. 影響：採用口述，要改寫 Rule 2，並重寫 `plan-with-class-diagram` Phase 3 的 READ 位置；採用既有，口述的規則不萃取。

## Bad Example

- 同一個衝突只丟出一句問題，使用者要自己去翻兩邊的規則，也看不出選哪一方會影響什麼。

1. 這條跟既有規則衝突，要用哪一個？
