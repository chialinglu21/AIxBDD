# Rule 1 - 每條規則以 `# Rule N - <Rule name>` 開頭

- 強度：必須
- 每條規則是一個一級標題，格式固定為 `# Rule N - <Rule name>`。
- `N` 從 1 開始連續編號，不跳號、不重複。
- `<Rule name>` 直接寫出規則要求什麼，只看標題就知道該怎麼做。
- `<Rule name>` 只放規則名稱，不夾帶強度、標籤等其他資訊。

## Good Example

- 編號從 1 連續遞增，標題直接說出要求，標題裡只有規則名稱。

```markdown
# Rule 1 - 一條需求只描述一件事

- 強度：必須
- 一條需求只寫一個系統行為。

## Good Example

- 帳號鎖定與密碼重設拆成兩條，各自可以單獨驗收。

1. 密碼連續輸錯 5 次時，帳號鎖定 15 分鐘。
2. 使用者可透過 Email 重設密碼。

## Bad Example

- 兩個行為寫在同一條，其中一個沒做好，整條就無法驗收通過。

1. 密碼連續輸錯 5 次時帳號鎖定 15 分鐘，並且可透過 Email 重設密碼。

# Rule 2 - 需求用具體數值描述

- 強度：必須
- 次數、時間、金額一律寫出數字與單位。

## Good Example

- 次數與時間都寫成數字加單位。

1. 密碼連續輸錯 5 次時，帳號鎖定 15 分鐘。

## Bad Example

- 用「太多次」「一段時間」代替數字，每個人理解的標準都不同。

1. 密碼錯太多次時，帳號鎖一段時間。
```

## Bad Example

- 編號從 1 跳到 3；「數值」只是主題名稱，看不出要求是什麼；標題還夾帶了 `【必須】`。

```markdown

- 次數、時間、金額一律寫出數字與單位。
```

# Rule 2 - 描述的第一行標示規則強度

- 強度：必須
- 描述條列的第一行固定寫 `- 強度：必須` 或 `- 強度：建議`，只有這兩種，不可省略、不可自創。
- `必須`：違反就不合格，要改到符合為止。
- `建議`：可以不遵守，但必須寫出不遵守的理由。
- 兩條規則互相衝突時，`必須` 優先於 `建議`；兩條 `必須` 互相衝突，代表規則本身要修正。

## Good Example

- 強度都寫在描述第一行，標題保持乾淨。違反就無法驗收的規則標 `必須`；少數需求本來就沒有觸發條件可寫（例如「首頁顯示公司 Logo」），所以這條標 `建議`。

```markdown
# Rule 1 - 一條需求只描述一件事

- 強度：必須
- 一條需求只寫一個系統行為。

## Good Example

- 帳號鎖定與密碼重設拆成兩條，各自可以單獨驗收。

1. 密碼連續輸錯 5 次時，帳號鎖定 15 分鐘。
2. 使用者可透過 Email 重設密碼。

## Bad Example

- 兩個行為寫在同一條，其中一個沒做好，整條就無法驗收通過。

1. 密碼連續輸錯 5 次時帳號鎖定 15 分鐘，並且可透過 Email 重設密碼。

# Rule 2 - 需求寫明觸發條件

- 強度：建議
- 每條需求以「當…時」或「…時」開頭，寫出什麼情況下會發生。

## Good Example

- 觸發條件寫在句首，讀者一眼就知道什麼時候會發生。

1. 密碼連續輸錯 5 次時，帳號鎖定 15 分鐘。

## Bad Example

- 沒寫觸發條件，看不出什麼情況下會鎖定。

1. 帳號會被鎖定 15 分鐘。
```

## Bad Example

- 第一條把強度塞進標題，描述裡沒有強度行；第二條的強度寫了自創的 `重要`，而且不在第一行，看不出違反時該怎麼處理。

```markdown
# Rule 1 - 一條需求只描述一件事【必須】

- 一條需求只寫一個系統行為。

- 強度：重要

- 觸發條件寫在句首，讀者一眼就知道什麼時候會發生。
```

# Rule 3 - 標題下方用條列描述規則內容

- 強度：必須
- 規則標題下方緊接條列 `- `，一條只寫一個要求或限制。
- 資料需要對照時用 markdown table，需要示範格式時用 code block，兩者都放在條列之後。
- 描述段落不寫範例，範例一律放到 `## Good Example`、`## Bad Example`。

## Good Example

- 每條條列只寫一個要求；需要對照的資料用表格收在條列之後；範例都放在 Good／Bad Example 裡。

```markdown
# Rule 2 - 需求用具體數值描述

- 強度：必須
- 次數、時間、金額一律寫出數字與單位。
- 不用「太多」「很快」「一段時間」這類形容詞。

| 形容詞     | 改寫          |
| ---------- | ------------- |
| 錯太多次   | 連續輸錯 5 次 |
| 鎖一段時間 | 鎖定 15 分鐘  |

## Good Example

- 次數與時間都寫成數字加單位。

1. 密碼連續輸錯 5 次時，帳號鎖定 15 分鐘。

## Bad Example

- 用「太多次」「一段時間」代替數字，每個人理解的標準都不同。

1. 密碼錯太多次時，帳號鎖一段時間。
```

## Bad Example

- 用一整段敘述取代條列，兩個要求混在同一句；還把範例寫進描述段落，和 Good Example 重複。

```markdown
# Rule 2 - 需求用具體數值描述

- 強度：必須

需求裡的次數跟時間要寫清楚、不要用形容詞，例如「密碼錯太多次要鎖一段時間」要改成「連續輸錯 5 次鎖定 15 分鐘」。

## Good Example

- 次數與時間都寫成數字加單位。

1. 密碼連續輸錯 5 次時，帳號鎖定 15 分鐘。

## Bad Example

- 用「太多次」「一段時間」代替數字，每個人理解的標準都不同。

1. 密碼錯太多次時，帳號鎖一段時間。
```

# Rule 4 - 每條規則依序附上 Good Example 與 Bad Example

- 強度：必須
- 描述條列之後依序放 `## Good Example`、`## Bad Example`，兩者都要有，順序固定。
- 兩個 Example 都用二級標題 `##`，名稱照寫，不改成「正確範例」「反例」等其他字。

## Good Example

- 描述之後先放 Good 再放 Bad，標題文字與層級都符合規範。

```markdown
# Rule 1 - 一條需求只描述一件事

- 強度：必須
- 一條需求只寫一個系統行為。

## Good Example

- 帳號鎖定與密碼重設拆成兩條，各自可以單獨驗收。

1. 密碼連續輸錯 5 次時，帳號鎖定 15 分鐘。
2. 使用者可透過 Email 重設密碼。

## Bad Example

- 兩個行為寫在同一條，其中一個沒做好，整條就無法驗收通過。

1. 密碼連續輸錯 5 次時帳號鎖定 15 分鐘，並且可透過 Email 重設密碼。
```

## Bad Example

- 缺少 Bad Example；Good Example 的標題改成「正確範例」，層級也變成 `###`。

```markdown
# Rule 1 - 一條需求只描述一件事

- 強度：必須
- 一條需求只寫一個系統行為。

### 正確範例

- 帳號鎖定與密碼重設拆成兩條，各自可以單獨驗收。

1. 密碼連續輸錯 5 次時，帳號鎖定 15 分鐘。
2. 使用者可透過 Email 重設密碼。
```

# Rule 5 - Example 開頭先用條列點出重點

- 強度：必須
- `## Good Example` 下第一段是條列，說明這個範例好在哪裡，只講重點。
- `## Bad Example` 下第一段是條列，指出和 Good 的差異或違反之處，只講差異。
- 條列之後才放實際的範例內容。

## Good Example

- Good 的說明點出「好在哪」，Bad 的說明點出「錯在哪」，都放在範例內容之前。

```markdown
# Rule 3 - 需求寫明觸發條件

- 強度：建議
- 每條需求以「當…時」或「…時」開頭，寫出什麼情況下會發生。

## Good Example

- 觸發條件寫在句首，讀者一眼就知道什麼時候會發生。

1. 密碼連續輸錯 5 次時，帳號鎖定 15 分鐘。

## Bad Example

- 沒寫觸發條件，看不出什麼情況下會鎖定。

1. 帳號會被鎖定 15 分鐘。
```

## Bad Example

- Good 沒有說明，直接放範例；Bad 的說明只寫「這是錯的」，沒有指出錯在哪裡。

```markdown
# Rule 3 - 需求寫明觸發條件

- 強度：建議
- 每條需求以「當…時」或「…時」開頭，寫出什麼情況下會發生。

## Good Example

1. 密碼連續輸錯 5 次時，帳號鎖定 15 分鐘。

## Bad Example

- 這是錯的。

1. 帳號會被鎖定 15 分鐘。
```

# Rule 6 - Example 用具體情境與資料完整示範

- 強度：必須
- 說明條列之後，用具體的情境與資料完整示範如何遵守（Good）或違反（Bad）規則。
- 呈現方式三選一：code block 列出 1..n 筆資料、條列式情境描述，或兩者混用。
- 名稱、數值、訊息文字都寫真實可用的值，不用 `<xxx>`、`...` 這類佔位符。

## Good Example

- 次數、時間、提示訊息都寫出來，讀者可以直接照著驗收。

```markdown
# Rule 3 - 需求寫明觸發條件

- 強度：建議
- 每條需求以「當…時」或「…時」開頭，寫出什麼情況下會發生。

## Good Example

- 每條需求都寫出觸發條件、次數與時間，驗收時可以直接照著測。

1. 密碼連續輸錯 5 次時，帳號鎖定 15 分鐘。
2. 鎖定期間嘗試登入時，顯示「帳號已鎖定，請 15 分鐘後再試」。

## Bad Example

- 沒寫觸發條件，看不出什麼情況下會鎖定、什麼情況下會顯示訊息。

1. 帳號會被鎖定 15 分鐘。
2. 顯示「帳號已鎖定，請 15 分鐘後再試」。
```

## Bad Example

- 和 Good 是同一條規則、同樣的說明，但範例裡的次數、時間、提示訊息都換成了 `<錯誤次數>`、`<鎖定時間>`、`<提示訊息>`。讀者看不出要輸錯幾次、鎖多久、畫面上顯示什麼，也就沒辦法照著驗收。

```markdown
# Rule 3 - 需求寫明觸發條件

- 強度：建議
- 每條需求以「當…時」或「…時」開頭，寫出什麼情況下會發生。

## Good Example

- 每條需求都寫出觸發條件、次數與時間，驗收時可以直接照著測。

1. 密碼連續輸錯 <錯誤次數> 次時，帳號鎖定 <鎖定時間>。
2. 鎖定期間嘗試登入時，顯示 <提示訊息>。

## Bad Example

- 沒寫觸發條件，看不出什麼情況下會鎖定、什麼情況下會顯示訊息。

1. 帳號會被鎖定 <鎖定時間>。
2. 顯示 <提示訊息>。
```

# Rule 7 - Good 與 Bad 用同一個情境對照

- 強度：建議
- 同一條規則的 Good Example 與 Bad Example 用同一個情境、同一組資料。
- 兩者的差異只落在這條規則規範的地方，其他內容盡量相同。

## Good Example

- Good 與 Bad 都在講「密碼輸錯後鎖定帳號」，唯一差異是次數與時間有沒有寫成數字，讀者一眼就看出規則在管什麼。

```markdown
# Rule 2 - 需求用具體數值描述

- 強度：必須
- 次數、時間、金額一律寫出數字與單位。

## Good Example

- 次數與時間都寫成數字加單位。

1. 密碼連續輸錯 5 次時，帳號鎖定 15 分鐘。

## Bad Example

- 用「太多次」「一段時間」代替數字，每個人理解的標準都不同。

1. 密碼錯太多次時，帳號鎖一段時間。
```

## Bad Example

- Good 講帳號鎖定，Bad 卻換成訂單審核，情境、用詞全都不同，讀者要自己猜哪個差異才是重點。

```markdown
# Rule 2 - 需求用具體數值描述

- 強度：必須
- 次數、時間、金額一律寫出數字與單位。

## Good Example

- 次數與時間都寫成數字加單位。

1. 密碼連續輸錯 5 次時，帳號鎖定 15 分鐘。

## Bad Example

- 用「很高」代替數字，每個人理解的標準都不同。

1. 訂單金額很高時，需要主管審核。
```
